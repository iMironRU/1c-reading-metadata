# Ответы к части 7

Ответы собраны здесь, а не под вопросами: подсказка, увиденная сразу
после вопроса, отменяет попытку вспомнить.

## § 7.1. Перечисления: список, закрытый навсегда

*Вопрос 1.* Пользователь не может добавить новое значение в перечисление — список зафиксирован при разработке. В справочник пользователь добавляет новые элементы в любой момент.

*Вопрос 4.* Предопределённый элемент — это элемент справочника, созданный разработчиком и защищённый от удаления. Но рядом с ним пользователь может добавить другие элементы — список остаётся открытым. Значение перечисления — часть закрытого списка; ни добавить, ни удалить его в пользовательском режиме невозможно.

*Упражнение «Спроектируй».* Статусы стоит реализовать перечислением: их набор фиксирован логикой бизнес-процесса, добавление нового статуса требует изменения логики системы (а значит, и конфигурации). Справочник был бы уместен, если бы статусы управлялись пользователем — например, в системе, где каждая компания сама настраивает свои этапы работы.

## § 7.2. Планы счетов и регистры бухгалтерии

*Вопрос 2.* Субконто — дополнительный аналитический разрез, привязанный к счёту. Без субконто остаток по счёту — это одна сумма. С субконто — детализированный учёт: остаток по счёту в разрезе каждого значения субконто (по каждому товару, по каждому складу, по каждому контрагенту).

*Вопрос 5.* Если субконто нет — остаток показывает только общую сумму по счёту без детализации. Например, «на счёте 51 — 500 000 рублей», но неизвестно, на каком именно расчётном счёте.

*Упражнение «Спроектируй».* К счёту 62 нужно добавить субконто с типом «СправочникСсылка.Контрагенты». После этого регистр будет хранить остаток не просто по счёту 62, а по счёту 62 в разрезе каждого контрагента — бухгалтер увидит долг отдельно по каждому покупателю.

## § 7.3. Регистры расчёта и планы видов расчёта

*Вопрос 1.* Регистр накопления просто суммирует приход и расход без учёта периодов и взаимодействия между записями. Зарплатные начисления могут влиять друг на друга (больничный уменьшает оклад за тот же период), требуют перерасчёта задним числом — для этого нужна специальная логика регистра расчёта.

*Упражнение «Спроектируй».* Если платежи корректируются за прошлые периоды и суммы зависят от периода действия — регистр расчёта подходит лучше: он умеет работать с перекрывающимися периодами. Регистр накопления подошёл бы для простого учёта «начислено — оплачено» без перерасчётов.

## § 7.4. Планы видов характеристик: прилагательные пользователя

*Вопрос 5.* Если фирма торгует разными группами товаров (канцелярия, электроника, одежда), у каждой группы свои характеристики. Добавить все возможные реквизиты в справочник «Товары» — значит создать огромное количество полей, большинство из которых будут пустыми для конкретного товара. ПВХ позволяет хранить только те характеристики, которые реально нужны каждому конкретному объекту.

*Упражнение «Спроектируй».* Добавить в дерево: (1) «ПВХ ВидыХарактеристикТоваров» — пользователь добавляет виды (Цвет, Размер, ...); (2) «Регистр сведений ХарактеристикиТоваров» — измерения: Товар (→Товары), ВидХарактеристики (→ПВХ ВидыХарактеристикТоваров), ресурс: Значение. Измерение «ВидХарактеристики» ссылается именно на ПВХ — это обеспечивает контроль допустимых видов: нельзя записать значение для характеристики, которой нет в плане.

## § 7.5. Бизнес-процессы и задачи

*Вопрос 3.* В «Канцтоварах» операции простые: поступление товара, изменение цены. Согласований нет, цепочки исполнителей нет. Бизнес-процессы нужны там, где одна операция проходит через несколько людей с контролем последовательности.

*Упражнение «Спроектируй».* Простой вариант: добавить в документ реквизит «СтатусСогласования» (перечисление: Новый / На согласовании / Согласован / Отклонён) и обязанность проведения только при статусе «Согласован». Это не хватит, когда: исполнителей несколько и у каждого своя роль; нужен контроль сроков; маршрут зависит от результата каждого шага.

## § 7.6. Роли и безопасность

*Вопрос 3.* Платформа требует хотя бы одну роль для входа в систему. Без роли пользователь не может авторизоваться — это обязательный элемент конфигурации.

*Упражнение «Спроектируй».*
```
Роль «Кладовщик»:
- Справочники Товары, Склады, Контрагенты: Чтение
- Документ ПоступлениеТоваров: Чтение, Создание, Проведение
- Отчёт ОстаткиТоваровНаСкладе: Открытие

Роль «Директор»:
- Все объекты: полный доступ
- Документ ПриказОбИзмененииЦен: Создание, Проведение
```

## § 7.7. Другие объекты дерева: константы, планы обмена, журналы документов, функциональные опции

*Вопрос 3.* Журнал документов — только представление. Данные хранятся в своих объектах (документах), журнал просто показывает их вместе в одном списке. Удаление журнала не удаляет документы.

*Вопрос 5.* Реквизит может быть недоступен из-за функциональной опции: она выключена, и реквизит скрыт или заблокирован. Также возможно ограничение по роли (нет права на запись).

*Упражнение «Спроектируй».* Нужен план обмена. В нём описать: узлы (конфигурация 1С и интернет-магазин), состав данных для отправки (остатки из регистра накопления) и получения (заказы → документы). Детальная настройка обмена — отдельная тема за рамками книги.
